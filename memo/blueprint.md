# Discord Bot を作りたい

## 機能
discordの会話上で出た技術用語を、必要に応じて簡単に説明してくれるBOTを作りたい

### 例
@BOT名 BFS

```
BFS【びーえふえす】

Breadth First Search, 幅優先探索

探索アルゴリズムのひとつ。グラフ構造などにおいて、始点からの距離が最も近い箇所から順番に探索していく手法。主にキューが使用される。
```

## 設計方針・参考資料
- BOTに単語名を聞くことで、意味を簡単に教えてくれる機能
    - 既に意味が登録されている場合、それを出力。でなければ、Geminiなどで緊急生成
- チャンネルにおける直近5件程度のメッセージについて、(或いは返信が読み取れるのであれば該当するメッセージ)説明できそうな単語を検知する機能
- 意味の登録・編集・削除ができる

### 参考資料
人狼ジャッジメントのチャットにて、CO, 黒, 吊るといった単語が出現すると、それを感知して意味が知れるボタンが出現する機能があったような。それが参考になりそう。

MCC内のみでの運用を想定するため、別に無機質なBOTでなくてもよさそう。万が一、全世界に公開することになったら、改めて考え直すべきか。
ただ、コスト面から考えても、性格は単一にした方が良さそう。以下のどれかが良さそう。

### 新データモデル

既存テーブルを直接大きく変えるのではなく、マイグレーションを作り、既存データをパブリック辞書として移行する。主要テーブル案は次のとおり。

#### `dictionary_entries`

- `id`: UUID、主キー
- `scope`: `public` または `local`
- `guild_id`: ローカル時は必須、パブリック時は `null`
- `word`, `full_word`, `japanese`, `summary`, `detail`, `pronounce`
- `normalized_word`: 検索・重複判定用
- `status`: `draft`、`pending`、`approved`、`rejected`
- `source`: `human`、`ai`、`seed`
- `created_by_discord_user_id`: 投稿者追跡用
- `reviewed_by_discord_user_id`: 審査者追跡用。AI審査の場合は別途審査種別を記録
- `review_comment`: 却下理由や確認事項
- `created_at`, `updated_at`, `reviewed_at`

制約として、`scope = local` なら `guild_id IS NOT NULL`、`scope = public` なら `guild_id IS NULL` を必須とする。承認済みデータの一意性は、パブリックでは `normalized_word`、ローカルでは `guild_id + normalized_word` を基準にする。

#### `word_aliases`

- `id`: UUID、主キー
- `entry_id`: `dictionary_entries.id` への外部キー
- `alias`: 表記ゆれ
- `normalized_alias`: 検索用
- `scope`, `guild_id`:検索範囲を明確にするため辞書項目と整合させる
- `source`: `human` または `ai`

エイリアスから別エイリアスへ連鎖させず、必ず辞書項目IDを直接参照する。これにより循環参照を防ぐ。

#### `guild_settings`

- `guild_id`: 主キー
- `local_dictionary_enabled`
- `local_entry_limit`: 初期値50
- `public_submission_enabled`
- `public_approval_enabled`
- `blocked_at`, `blocked_reason`
- `created_at`, `updated_at`

MCCだけでパブリック承認を許可する場合は、環境変数ではなくこの設定で対象サーバーを明示する。

#### `web_access_tokens`

- `id`: UUID、主キー
- `token_hash`: 生のトークンは保存しない
- `purpose`: `add` または `manage`
- `guild_id`, `discord_user_id`
- `expires_at`, `used_at`, `revoked_at`

登録URLは短時間だけ有効な単回利用トークンとする。管理URLは長寿命の共有URLにせず、アクセスのたびにDiscordから再発行する。

#### `submission_events` と `audit_logs`

投稿回数、AI審査結果、却下、編集、削除、承認、制限発動を記録する。荒らし判定と管理操作の追跡に使用し、説明本文など不要な個人情報は重複保存しない。


## 今後の開発について

### ローカルじしょこーど
各サーバー内での造語、内輪ネタにも対応させたい。discord server毎に固有のIDが振られているっぽいため、別のリストにIDと一緒に格納させておく。サーバーごとに50件程度登録できれば十分かも？以下、今までのじしょこーどをパブリックと呼称。同時に、現状個人サーバーのみで動作する状態のため、それを解除。

### 追加用のweb UI
`/add` を単体で送ることによって、登録用のURLを発行する。URLを踏んだ先で必要事項を記入することで登録できる仕組み。 Reactを使うことでUIを作る。ローカル・パブリック両方に対応させる。ローカルは鯖主の承認、パブリックはAIの確認を必ず通す。
同様に、`/manage` を単体で送ることで、管理用のURLを発行。URLを踏んだ先でローカルの管理ができるようにもしたい。

### 公開前に
ざっと200単語程度、必要そうな単語とその意味を予め生成させておく。目視または別のAIの確認によって間違いがないようにし、accept状態にしておく。また、publicに対する承認権限はオフにしておく。ただし、MCC内での運用時はオンにしておいても良さそう

### さらなる安全性について(完了)
必ず、文字数上限を設定しておく。個人、AI共にその制限を超えないように保守。また、パブリックの新規登録は何らかの制限を掛ける。また、パブリックに対してふざけた登録を繰り返す場合、その鯖での利用を制限させてもいいかも。

### エラーハンドリング(完了)
AIが false を返した場合、エラーが発生して上手にハンドリングできていないように見受けられる。修正必須。

### 表記ゆれについて
新規登録時に表記ゆれを3~4種類考えるようにプロンプトを修正する。出力された表記ゆれおよび元となる単語のうち、最も一般的なものを判定してもらう。他の単語からその単語に修正できるよう、表記ゆれのリストに格納。

### 表記ゆれ

#### 生成と保存

AIの出力スキーマへ `aliases` を追加し、0〜4件の表記ゆれ候補を返させる。候補には大小文字、全角・半角、空白・ハイフン、略称、カタカナ表記などを含められるが、意味の異なる語や単なる関連語は含めない。

プロンプトでは、元の入力語と候補から最も一般的な表記を `canonicalWord` として1件選ばせる。ただしAI判定だけで既存の正規語を変更せず、次の決定規則を適用する。

1. 既存の承認済み辞書または表記ゆれに一致する場合は、既存の正規語を維持する。
2. 一致しない新規語では、AIの `canonicalWord` を候補として審査画面へ出す。
3. 人または所定の審査フローで承認後、正規語を辞書へ、その他を `word_aliases` へ保存する。
4. 正規化後に正規語と同一になる候補、候補同士の重複、空文字は除外する。
5. 他の承認済み項目を指す表記ゆれは自動保存せず、衝突として審査へ回す。

検索時は完全一致を優先し、その後に正規化した表記ゆれを検索する。パブリックとローカルの優先順位は辞書検索と同じにする。曖昧一致や編集距離検索は誤誘導の可能性があるため第1段階には含めず、候補提示機能として別途検討する。

#### 正規化規則

検索用の正規化はUnicode NFKC、前後空白除去、連続空白の統一、英字の小文字化までを基本とする。記号除去は `C++`、`C#`、`.NET` などを壊すため一律には行わない。日本語のひらがな・カタカナ変換も意味や一般表記を変える可能性があるため、明示的な表記ゆれとして管理する。

#### 受け入れ条件

- `BFS`、`bfs` など承認済みの表記ゆれから同じ項目を取得できる。
- `C++` と `C` のような別語が正規化で衝突しない。
- AIが重複候補や既存の別項目を返しても、自動的に誤った紐付けを作らない。
- ローカルの表記ゆれが別サーバーへ漏れない。
